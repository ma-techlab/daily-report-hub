# 納品時の設定と購入者への確認事項

契約前の要件確認は、先に「購入前ヒアリングシート」を使います。このチェックリストは、要件確定後の設定・動作確認・納品判定に使います。

## 購入者に用意してもらうもの

- 運用に使う Google アカウント。このアカウントがスプレッドシート、フォーム、Apps Script、トリガーの所有者になる。
- 店舗ごとの店舗ID、正式な店舗名、日報責任者のメールアドレス、定休曜日、利用開始時の有効／無効。店舗IDと店舗名は重複させない。
- 本部通知の宛先メールアドレス1つ。
- 未提出リマインドの時間帯、週次まとめの時間帯、残食率と提供不足率の基準。
- 試験送信の宛先と、実メール送信を開始する日。

## スクリプト プロパティ

| キー | 入力値 | 確認事項 |
|---|---|---|
| `HQ_EMAIL` | 本部のメールアドレス | 空の場合、本部宛ては送信されず送信ログに残る |
| `DRY_RUN` | 試験中は未設定または `true`、本番開始時のみ `false` | `false` と小文字で一致した場合だけ実送信 |
| `REMIND_HOUR` | 0〜23の整数 | 既定は15。範囲外などは15に戻る |
| `WEEKLY_HOUR` | 0〜23の整数 | 既定は8。範囲外などは8に戻る。週次は月曜日 |
| `LEFTOVER_ALERT_RATE` | 0〜1 | 既定は `0.15`（15%）。基準を超えたとき要対応 |
| `SHORTAGE_ALERT_RATE` | 0〜1 | 既定は `0.1`（10%）。基準を超えたとき要対応 |

`FORM_ID` は初期設定実行時に自動で保存されるため、購入者が入力しない。

## 初期設定の実施順

1. 購入者の Google アカウント管理下にスプレッドシートと Apps Script を用意し、`src/` の4つの `.js` と `appsscript.json` を反映する。
2. スクリプト プロパティに値を入れる。`DRY_RUN` は安全のため `true` のままにする。
3. スプレッドシートを開き直し、「日報ハブ」メニューの「初期設定」を一度実行して必要なシートを作る。店舗が未登録のため停止するメッセージは想定どおり。
4. 「店舗マスタ」を本番情報で登録する。本番ファイルにデモデータを入れない。
5. もう一度「初期設定」を実行し、必要な Google の権限承認を運用所有者のアカウントで行う。フォームとトリガーが作られ、回答用URLが表示される。
6. フォームを開き、選択できる店舗と各質問を確認する。以後マスタを変更したときは「フォームの店舗を更新」を実行する。
7. `DRY_RUN=true` のまま、通常日報、同日修正、衛生未実施、残食数超過のエラー、未提出リマインド、週次まとめを確認する。週次は通常営業日と定休日のテスト日報を用意し、定休日分が集計から除かれることも確認する。
8. トリガーが `handleFormSubmit`、`remindMissing`、`sendWeeklySummary` の3つで、重複していないことを Apps Script のトリガー画面で確認する。
9. 購入者の承認後、試験宛先で `DRY_RUN=false` にして実メールを1回確認する。本番開始日まで実送信しないなら、確認後に `true` へ戻す。

## 納品前の完了確認

- [ ] 所有者、編集者、店舗担当者へのフォームURL共有方法が決まっている
- [ ] 店舗マスタのID・店舗名の重複、メールアドレス、定休日、有効状態を目視した
- [ ] 店舗ID・店舗名の空欄または重複で初期設定／フォーム更新が停止することを検証用データで確認した
- [ ] 設定時間と閾値を購入者が承認した
- [ ] 範囲外の時刻・閾値が既定値に戻ることを検証用設定で確認した
- [ ] `DRY_RUN` の最終値と実送信開始日を確認した
- [ ] 正常入力、修正、要対応、受付エラー、未提出、週次集計を購入者の環境で確認した
- [ ] 定休日のテスト日報が「日報」に残り、週次の提出数・提供食数・残食率・要対応件数から除かれることを確認した
- [ ] 「送信ログ」と Apps Script の実行履歴の確認方法を引き継いだ
- [ ] バックアップ方法、データの保管・削除ルール、Google アカウントの管理責任を購入者と合意した

Apps Script の時刻トリガーは指定した時間帯に実行され、分単位の時刻は指定していません。送信量は Google アカウント側の当日クォータにも依存します。
